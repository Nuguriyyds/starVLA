# UMI 性能基线（2026-09-20）

本轮基于 `2b2a568` 增加可关闭的性能测量。保留模型、world-pose 16D
动作表示、四视图、固定归一化、梯度累积与完整恢复语义。没有启动全量训练。

测试时的 `starVLA/**/*.py` 内容指纹：
`467c68a65183fb295ac9b26db9d845b5f60bde70fa7a07e9d4ae514b909f6d81`。
测试是在上述基线的未提交改动上完成，最终提交会改变 Git HEAD；不改写旧 run
的代码身份以跨提交恢复。下述工程结果与正式全量/多 PPU 验收分开。

## 环境与口径

- 单 PPU-ZW810E，96 GiB；没有与另一组性能任务同时运行。
- Python 3.12，厂商 Torch 2.7.0，Transformers 4.57.1，Accelerate 1.12.0，
  Diffusers 0.37.1，PyArrow 23.0.1，PyAV 17.0.0；没有更改环境依赖。
- 每卡 batch=1，梯度累积=2，FP32 参数与普通 AdamW，`fused=False`、
  `foreach=False`；沿用 VLM 内部 BF16 和动作头 FP32 桥接。
- 工程数据：原有 A/B 视图和已有工程 mean/std；不是正式训练/验证划分。
- 两组从同样初始化开始，原样调用 `train_umi_pretrain`，没有另写优化循环。
- 回放仅缓存每阶段 sampler 前64个样本的 PIL/语言/归一化 state/action，
  sampler、原样本身份、顺序与长度不变；缓存外访问报错。不缓存 VLM 特征，
  不冻结主干。回放 worker=0，真实读取 worker=2。
- 默认22次完整更新，其中前2次预热，后20次测量；A21次、B1次。
  阶段边界与结束分别完整保存一次，最后评测一次。循环设置1200秒软预算，
  安全保存不会被强杀。完成后新进程重新加载端到端 run，不额外更新。
- 设备同步及 events 已在本机验证。前2次更新使用事件细分；稳定区间只在
  区间边界同步。细分 host 时间可能重叠，不能求和当作设备计算时间。
- “窗口/秒”是训练窗口曝光，不是不同数据小时数。进程总吞吐包含导入、
  初始化、预加载、评测、保存等；稳定吞吐排除启动、评测、保存和阶段重建。
- 主机资源是离散时刻采样，RSS 相加可能重复计算共享页；不等于精确物理
  内存峰值。设备 `allocated`、`reserved` 与设备总占用分别记录。

## DataLoader-only

全量候选池只读取样，不对其进行模型更新。当前 sampler 的前256个窗口
固定一致，块大小128；另从物理文件列表等距选16个文件，构造48次跨文件
读取。prefetch=2，worker=0时不设置多进程预取选项。

sampler 顺序覆盖2个 episode、2个 Parquet、8个视频，最长连续同 episode
为128个样本。补充跨文件序列覆盖16个 episode、16个 Parquet、64个视频，
最长连续同 episode 为1。以上是文件/episode 局部性，不代表任务语义均衡。

sampler 顺序的行组/文件/视频句柄命中率约99.2%、98.4%、96.9%（分别为
0/2/4 workers，每个 worker 独立缓存）。补充跨文件序列的视频句柄命中率
为0，仍可持续读取。这里的“视频命中”指打开的容器，**不是已解码帧缓存**。

上述组按0→2→4顺序运行，后组可能受系统缓存预热影响，不应把比值当成
纯 worker 数的因果加速比。没有清除系统/存储缓存。256/48窗口只是有边界
的基线，不能证明长时间稳定性或覆盖十亿帧的所有情况。

## 原始跨文件压力序列发现的读取问题

原序列从每个选中 episode 的第一个有效窗口开始。0/2/4 worker 都在第三个
窗口失败，未计入成功吞吐；错误、原序列与完整交付前缀均保留。

- `dataset_index=126293227`，`episode_index=34300`，`frame_index=0`。
- 低维：`data/chunk-000/file-438.parquet`。
- 右头相机：`videos/observation.images.head_right/chunk-001/file-557.mp4`。
- 元数据片段起点：286.066677666 秒；最近视频帧：286.066677 秒。
  最近帧比起点早 **0.666 微秒**，被 `start <= time` 的片段边界判断排除。
- 下一帧：286.100013 秒，误差0.033335334秒，比既有容差
  0.033334333秒大约1.001微秒，因此抛错。

这能证明该读取器存在片段边界精度不一致的具体案例，不能据此认定任务标签
错误或整段数据损坏。没有放宽容差、重新清洗数据或修改索引。

为继续测跨文件性能，补充序列把**同样16个文件**的首个有效区间定位到区间
中点，每个文件仍读3次。所有样本都使用同一确定规则，不通过自动跳过失败
来凑成功数量。补充结果不能替代原始首帧序列的失败结论。下一轮需要单独
修复并验证帧定位边界，再声称数据管线能够覆盖这些首帧样本。

全部字节摘要相同。复核在计时任务结束后进行，没有与吞吐测量争抢资源。

稳定吞吐只差约0.46%。这是固定顺序的单次短测，没有统计证据说明真实读取
更快；支持的是：**此工程数据及配置下，去掉磁盘与解码没有带来明显加速**。
两worker的供给约23.28窗口/秒，高于模型约2.84窗口/秒，实际本地等待也很小。
不把这个结果外推为64卡共享存储仍足够，也不外推到未见过的全部episode。

回放组测量期平均每次更新，host计时的forward（含processor/传输）约0.193秒，
backward约0.268秒，optimizer约0.062秒。其异步提交、检查和设备执行可以
重叠；不能机械求和，也没有据此声称某个Attention算子就是瓶颈。
后续若优化稳定训练，优先细分模型侧预处理/计算，而非盲目增加worker。

每个完整checkpoint约42.08 GiB。单次保存实测306.24～391.19秒，主要成本
是状态写入以及文件读取/摘要校验。`checkpoint_file_hash` 包含存储读取，
不能解释为纯SHA算力成本；文件fsync合计不足0.05秒/组。没有删除摘要、fsync
或完成标记。两次保存占进程墙钟约88%～89%；短跑总吞吐因此不代表正式训练
效率。正式保存间隔需结合保存时间和可接受重算量设置，不能照搬工程频率。

新进程以原身份重新加载已完成的端到端run，退出码0，没有额外更新。
恢复完整性核验37.694秒，状态加载27.143秒；含导入、模型构造等的进程
墙钟121.361秒。这次恢复读到了较热缓存，不能用它否定前面保存阶段较慢的
摘要读取。恢复进程观测RSS约12.760 GiB，GPU分配峰值42.093 GiB；它没有
继续执行前后向，不能拿42.093 GiB代替实际训练的62.198 GiB预算。

两组第一次损失都是9426.3359375，后续损失轨迹不同。本轮不将其归因于
数据读取或某个特定算子，也不把吞吐对照当成数值等价性验证。
在同一更新21处，Python、NumPy、Torch CPU、Torch CUDA及loader generator
的保存状态全部逐项相同，排除了“到该点随机数状态不同”这一解释；这仍然
不能证明每一步设备算术或参数完全相同。真实PPU等价性仍需单独验收。

## 下一项工作

1. **先修复并定向验证视频片段起点的时间精度问题**，不把它扩大成重新清洗
   全量任务。原失败样本应成为回归案例，补充中点压力测试不能替代它。
2. 性能上优先处理保存频率与当前存储的checkpoint读写成本；先保留完整性
   要求。当前单卡配置下保持2worker即可，没有证据需要增加到4或8。
3. 若继续优化稳定更新，下一轮先拆开processor/传输和模型计算，再逐项测
   精度或算子调整。真实PPU数值重复性、双PPU DDP仍是独立的后续验收。

本轮不提出某个目标加速百分比，不决定正式语义划分，也不据此选择ZeRO/FSDP。
